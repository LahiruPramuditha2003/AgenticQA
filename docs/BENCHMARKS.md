# Benchmarks

How AgenticQA's accuracy is measured, why the obvious measurement is wrong, and how to reproduce the
numbers yourself.

---

## The problem with pass rates

**A Playwright PASS does not mean the test tested anything.**

This is not a hypothetical. Early in development this suite reported **19/20 (95%)** on a held-out app. An
audit of the generated specs found that roughly **1 in 20** actually tested what the prompt asked:

- all 20 started at `/` and never navigated by URL again,
- 11 of 20 asserted a heading that was **already visible before any action**,
- **not one** contained a `fill`, `select` or `check` — despite seven form-centric prompts.

Every one of those passed. A test with no assertions cannot fail; a test that asserts something already on
screen passes without exercising anything. Pass rate cannot see the difference, so pass rate is not a
measure of quality.

## The substantive rate

Every benchmark run is therefore **audited for what the generated spec actually does**
(`scripts/auditSpecSubstance.js`). It parses each spec's step markers, `goto` paths and assertion targets,
compares them with the prompt, and classifies:

| Verdict | Meaning |
|---|---|
| **VACUOUS** | No assertions at all. A test that cannot fail. |
| **UNDER_TESTED** | The prompt demands a fill/select/check the spec never performs. |
| **OFF_TARGET** | Never leaves the start page **and** asserts something the prompt never mentioned. |
| **SUBSTANTIVE** | Exercises the request. |

**The substantive rate is the number we quote.** It is a deliberate **lower bound** — when unsure, the
auditor says SUBSTANTIVE.

> Two tempting stricter heuristics were tried and **withdrawn**, because they scored the known-good suite
> at 0/20: "the assertion target must appear in the prompt", and "the prompt's quoted text must appear in
> the spec". Both break on legitimate paraphrase — a knowledge pack deliberately turns "verify a welcome
> message" into asserting `"Total Orders"`. Tests guard against reintroducing them.

## Results

Measured 2026-08-11.

| App | Pack | Tuned? | Raw | **Substantive** |
|---|---|---|---|---|
| `apps/demo-web`, 5 browsers | hand-written, 15 flows | yes | 19/20 | **18/20 (90%)** |
| `apps/taskflow-web`, chromium | **auto-generated** | **no** | 20/20 | **19/20 (95%)** |

### Why the second row is the one that matters

`apps/taskflow-web` is **held out**. It was built to be deliberately disjoint from the development app in
domain, vocabulary, routes and widget mix. It ships **no** hand-written knowledge pack — its pack is
generated by the same command any user would run. The engine was never tuned against it, and
[the contributing guide forbids tuning it](../CONTRIBUTING.md#7-the-held-out-app-stays-held-out).

**It scores above the app the engine was built on.** That inversion is the strongest evidence in this
project that AgenticQA generalizes rather than memorizes — and it reframes the tuned app's two remaining
failures as a gap in *that app's hand-written pack*, not a gap in the engine.

### How it got there

The held-out app's trajectory, which is more informative than the final number:

| Milestone | Substantive |
|---|---|
| First run with a generated pack | 25% |
| After fixing input-type handling | 30% |
| After fixing cross-page element pooling | 60% |
| After interaction-aware flow retrieval | 85% |
| After adding the `filter` flow family | **95%** |

Every one of those jumps came from a defect found by *measuring*, not by intuition. Three of them were
invisible to pass rate entirely.

## Reproducing it

Requires a source checkout, an API key, and time (~35 min for the 5-browser run).

```bash
cd packages/orchestrator
npm run build

# demo-web — the full matrix
node scripts/batchRunTemplates.js --from=1 --to=20 --save-logs

# taskflow-web — the held-out app, chromium
node scripts/batchRunTemplates.js --from=1 --to=20 \
  --app=apps/taskflow-web \
  --templates=benchmarks/TEST_TEMPLATES_TASKFLOW.md \
  --project=chromium --save-logs
```

Both numbers are printed side by side at the end.

> ⚠️ **Before running:** confirm `apps/demo-web/.agenticqa/knowledge.json` is unmodified
> (`git diff --stat` on it must be empty). Running **Generate Knowledge Pack** against demo-web replaces
> its hand-curated pack, and every downstream number is then measuring something else.

**Re-score a past run without re-running it:**

```bash
node scripts/auditSavedArtifacts.js --app=demo-web --templates=benchmarks/TEST_TEMPLATES.md
```

## Offline metrics

These run in seconds with no network, and are what catch regressions between live runs.

| Command | Measures | Current |
|---|---|---|
| `npm run eval:flowindex` | Flow retrieval on a hand-written pack | hit@1 19/19, MRR 1.000 |
| `npm run eval:generatedpack` | Flow retrieval on a **generated** pack | hit@1 16/20, hit@3 20/20 |
| `npm test` | 456 unit tests | all green |

The two retrieval evals are separate on purpose: they measure different things and have, on occasion,
moved in **opposite directions** for the same change. Intent tags improved the generated pack
(13 → 14/20) while making a hand-written one worse (17 → 13/19) — machine-written flow text is
vocabulary-poor, so "how a user would say it" is genuinely new information there and merely noise in a
pack a human already wrote.

Two golden fixtures lock behaviour exactly: every deterministic **plan**, and every generated **spec**. A
diff in either is a decision to be reviewed, not a surprise.

## Three ideas rejected by measurement

Recorded so they are not retried on intuition. Each is reproducible with the evals above.

1. **Embeddings for flow retrieval.** Lexical 17/19 beat semantic 14/19 and hybrid 15/19. Semantics are
   off by default.
2. **A confidence threshold for abstaining.** The one prompt that *should* abstain scored the highest
   confidence of any. Abstention is triggered structurally instead.
3. **Hand-authored intent tags** on a hand-written pack: 17 → 13/19. See above for why the same
   intervention helps a generated pack.

---

## Reading any of these numbers

- **Quote the substantive rate**, always.
- **They are snapshots of a moving target** — free model availability alone can shift them.
- **They come from two apps.** That is two more than most such claims, and still only two.
